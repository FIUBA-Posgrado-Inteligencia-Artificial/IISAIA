"Imagínense a este caballo. Potente. Libre. Y supongamos que la estrategia es pedirle que se comporte. Decirle 'no cometas errores'. Eso no funciona — ni con un caballo, ni con un modelo."

"Lo que funciona es esto. La misma potencia, canalizada por un arnés. Tira de tu carreta hacia donde vos querés. Esa es la disciplina: harness engineering. No es pedirle al modelo que sea mejor — es diseñar el arnés que canaliza lo que ya hace."

Las dimensiones del harness

Ocho decisiones, y cada una se configura en algún archivo del proyecto:

Instrucciones persistentes

Lo que el agente lee al arrancar cada sesión: convenciones, restricciones, cómo se trabaja en este repo.

Skills y comandos

Procedimientos guardados que se invocan por nombre: los escribís una vez y se repiten igual.

Tools disponibles

Qué puede ejecutar y qué no. Se amplía conectando servidores externos.

Permisos

Qué corre sin preguntarte, qué pide confirmación y qué queda bloqueado.

Modelo

Cuál atiende cada tarea: el más capaz para diseñar, uno más barato para lo mecánico.

Effort

Cuánto piensa antes de actuar. Se paga en tokens y en tiempo de espera.

Manejo del contexto

Qué se carga, cuándo se compacta y qué se delega a una ventana aparte.

Verificación automática

Qué corre solo después de cada cambio: tests, linters, chequeos que devuelven señal.

Ocho clicks, una card cada uno. No leerlas: nombrar y seguir.

Cada dimensión es algo que se configura, no una abstracción.

"Diseñar un harness es decidir ocho cosas, y lo importante es que ninguna es abstracta: cada una es un archivo o un parámetro que vas a tocar."

"Una: las instrucciones persistentes. Lo que el agente lee solo al arrancar cada sesión, sin que se lo pidas: las convenciones del proyecto, las restricciones, cómo se trabaja acá. Es lo primero que se escribe en cualquier repo con agentes."

"Dos: skills y comandos. Procedimientos guardados que se invocan por nombre. Si un flujo lo repetís tres veces, lo escribís una y de ahí en adelante sale igual siempre."

"Tres: qué tools tiene disponibles. Leer, editar, correr comandos, buscar en la web. Y se amplía conectando servidores externos que agregan tools nuevas: la base de datos, el tracker de tickets, lo que uses."

"Cuatro: permisos. Qué corre sin preguntarte, qué pide confirmación y qué está prohibido. Es el único de los ocho que es una barrera dura, no una instrucción."

"Cinco: qué modelo atiende cada tarea. No siempre querés el más caro: el más capaz para diseñar o depurar algo difícil, uno más barato y rápido para lo mecánico."

"Seis: cuánto esfuerzo le pedís antes de actuar. Los modelos actuales tienen una perilla de cuánto razonan, y eso se paga en tokens y en tiempo de espera. Para un cambio trivial, poner el máximo es tirar plata."

"Siete: cómo manejás el contexto, que es todo lo que acabamos de ver: qué se carga, cuándo compactás y qué mandás a resolver en una ventana aparte para no ensuciar la principal."

"Y ocho: qué se verifica solo. Los tests, el linter, el chequeo que corre después de cada cambio y le devuelve el resultado al agente sin que vos lo pidas. Es lo que convierte 'creo que anda' en 'pasó'."

La frontera con context engineering

Los límites son difusos. "Qué contexto cargás" es parte del harness y es lo que define context engineering. Hay solapamiento.

Algunos usan "harness" específicamente para todo lo que rodea al modelo en runtime: el system prompt, las definiciones de las tools, la lógica de reintentos, la orquestación de sub-agentes, los pasos de verificación.

Eso, en esa lectura, es distinto del modelo en sí y de un prompt suelto. Es la capa de runtime que envuelve a los dos.

Honestidad disciplinaria: la división context / harness no es limpia.

"Una aclaración honesta antes de seguir: los límites entre context engineering y harness engineering son difusos. Qué contexto cargás es parte del harness, pero también es lo que define context engineering. Y hay un tercer término que algunos usan, 'agent engineering', que se pisa con los dos. La lectura que nos sirve es esta: algunos usan harness específicamente para todo lo que rodea al modelo en runtime — el system prompt, las definiciones de tools, la lógica de reintentos, la orquestación de sub-agentes, los pasos de verificación. Visto así, el harness es la capa de runtime que envuelve al modelo y a los prompts sueltos. No es el modelo, no es un prompt — es lo que los hace operativos como agente. Y si les suena, es porque es el programa externo del principio de la clase, visto ahora como algo que se diseña."

Tres niveles para dirigir un agente

Prompt engineering

una interacción

El input bien diseñado: instrucciones, restricciones, ejemplos.

Context engineering

una sesión

Controlar qué ve el modelo: cargar lo necesario, mantener la señal, compactar o resetear cuando se llena.

Harness engineering

múltiples sesiones

La capa de runtime que persiste entre sesiones: prompt, tools, contexto, feedback, verificación, descomposición.

El programa externo que envuelve al modelo se diseña.

Lo que persiste de una sesión a otra vive en archivos que podés leer y cambiar.

Las tres cards. Click: el bridge.

Cierre de Parte 1: tres niveles anidados; el harness es lo que persiste.

"Cerramos la Parte 1 con las tres ingenierías. Prompt: una interacción. Context: una sesión — qué entra, qué se mantiene, qué se suelta. Harness: la capa de runtime que persiste entre sesiones — prompt, tools, contexto, feedback, verificación, descomposición. Por eso su alcance son múltiples sesiones: la ventana de una sesión se va, el harness queda."

"Y fíjense que el harness no es algo nuevo en la clase: es el programa externo que dibujamos al principio, la caja punteada alrededor del LLM. La diferencia es que ahora lo vemos como algo que se diseña. Lo que persiste de una sesión a otra vive en archivos concretos, que podés abrir, leer y cambiar. En la Parte 2 vamos a abrir esos archivos uno por uno."
