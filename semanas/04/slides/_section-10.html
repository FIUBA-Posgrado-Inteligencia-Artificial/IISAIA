Antes de cada tool call: deny, después ask, después allow

Si la tool call matchea… Resultado
1 una regla deny Bloqueada, sin prompt
2 una regla ask Pide confirmación, aunque también matchee allow
3 una regla allow Corre sin preguntar
4 ninguna regla Decide el modo: en Manual (default), pregunta

La primera coincidencia en ese orden decide. Un deny le gana a cualquier allow, sin importar cuál sea más específico ni en qué archivo esté cada uno.

El orden es fijo: deny, ask, allow. La especificidad no lo cambia.

Evaluación por orden de lista; lo que no matchea nada lo resuelve el modo.

"Tercera pregunta. Cuándo se evalúa. Antes de cada tool call, y en un orden fijo. Primero deny: si matchea, bloqueada, sin prompt. Después ask: si matchea, te pregunta, aunque haya un allow que también la cubra. Después allow: corre sin preguntar. Y si no matchea ninguna regla, decide el mode, el dial que vimos al abrir la sesión; en Manual, que es default, te pregunta. La primera coincidencia en ese orden gana, y la especificidad no importa: si tenés Edit de openapi.yaml en el allow del proyecto y alguien pone el mismo Edit en un deny local, la edición queda bloqueada. Eso lo vamos a ver en el demo."

Sintaxis: Tool(pattern)

Tool(pattern)
  • Bash(uv sync) · comando exacto.
  • Bash(git push *) · espacio y *: matchea git push origin main y también git push a secas.
  • Bash o Bash(*) · cualquier comando Bash.
  • Edit(./backend/**) · glob de path: cualquier archivo bajo backend/, recursivo.
  • Read(./.env) · un archivo; típico en deny.
  • WebFetch(domain:fastapi.tiangolo.com) · un dominio.

Cada ejemplo es un tipo distinto de pattern.

Comando exacto, wildcard, todo Bash, glob de path, archivo, dominio.

"Cuarta pregunta. Cómo se usa. La sintaxis es Tool, paréntesis, pattern. Bash(uv sync) es un comando exacto. Bash(git push *), con espacio y asterisco, matchea git push con cualquier argumento, y también git push a secas; el asterisco puede ir en cualquier posición y matchea cualquier texto. Ojo que Bash solo, o Bash(*), es cualquier comando: ponerlo en allow es darle la terminal entera. Edit(./backend/**) es un glob de path, cualquier archivo bajo backend. Read(./.env) es un archivo puntual, el caso típico de deny. Y WebFetch con domain dos puntos limita el fetch a un dominio."

Cuatro cosas que confunden de permisos

  • Un deny cubre una tool y un patrón, no una intención. Read(./.env) frena la tool Read, pero no un cat .env vía Bash ni un script de Python que abra el archivo, si esos comandos están permitidos. No es una frontera de seguridad.
  • Las lecturas no piden permiso. Leer archivos, Grep y comandos de solo lectura (ls, cat, git status) corren sin prompt dentro del proyecto.
  • Los wildcards no atraviesan && ni ;. Bash(uv run uvicorn *) en allow no cubre uv run uvicorn app && rm -rf .: no se cuela un segundo comando por concatenación.
  • Un Bash(rm -rf *) en deny no frena todas las formas de borrar. /bin/rm -rf o sh -c '...' no matchean el patrón. Lo que no querés que pase, mejor que tampoco esté habilitado por otro lado.

El primero es el más importante: deny no es sandbox.

Límites reales del sistema: patrón vs intención, lecturas libres, encadenamiento, variantes de un comando.

"Quinta pregunta. Qué confunde. Uno: un deny cubre una tool y un patrón, no una intención. Read de .env bloquea la tool Read sobre ese archivo, pero si Claude puede correr cat por Bash, o un script de Python que lo abra, el deny no se entera. Por eso el demo-repo acota uv run python a un solo script. Dos: las lecturas no piden permiso. Leer archivos, grep, ls, git status, corren sin prompt dentro del proyecto; por eso no hace falta un Read del proyecto en allow. Tres: los wildcards no atraviesan && ni punto y coma. Un allow de uv run uvicorn con asterisco no cubre uvicorn seguido de rm -rf. Y cuatro: un deny de Bash matchea texto. /bin/rm -rf, o un sh -c con el comando adentro, no matchean rm -rf asterisco. Si algo no tiene que pasar nunca, la defensa real es no habilitar caminos alternativos, y para aislar de verdad, un contenedor."

Reglas del runtime, determinísticas, antes de cada tool call

Los permisos son reglas del runtime evaluadas antes de cada tool call: primero deny, después ask, después allow; lo que no matchea lo decide el modo. Una regla escrita acá no se ignora ni se reinterpreta, pero cubre una tool y un patrón, no una intención.

Los permisos limitan qué hace el agente. Las skills van del otro lado: le dan procedimientos que no traía, cuándo hacer cada paso y en qué orden.

"Cerramos permisos. Son reglas del runtime evaluadas antes de cada tool call, en un orden fijo: deny, ask, allow; y lo que no matchea ninguna lo decide el modo. Una regla escrita acá no se ignora ni se reinterpreta, con un límite claro: cubre una tool y un patrón, no una intención. Y el puente a lo que sigue: todo esto fue sobre limitar qué hace el agente. Las skills van del otro lado: le dan procedimientos que no traía, cuándo hacer cada paso y en qué orden. Limitamos por un lado, extendemos por el otro."
