Un mismo mecanismo, dos formas: skill y command

  • Skill: un directorio con SKILL.md. Empaqueta un procedimiento completo (frontmatter, fases, anti-patterns, archivos de soporte). Claude puede cargarla por su cuenta cuando la tarea matchea su description.
  • Command: un solo archivo en .claude/commands/. Es la forma corta, ideal para un atajo que disparás vos.
  • Las dos crean /nombre. El nombre sale del directorio o del archivo. Si una skill y un command se llaman igual, gana la skill.
  • → La skill es la forma completa. El command es la forma de un archivo.

Tres ítems y el callout; el tercero es el que se confunde.

Skills y commands se fusionaron: son dos formas del mismo mecanismo.

"Primera pregunta: qué es. Mucha documentación vieja las presenta como dos cosas separadas, pero hoy son el mismo mecanismo con dos formas. Una skill es un directorio con un SKILL.md adentro: empaqueta un procedimiento completo, con frontmatter, fases, anti-patterns y, si hace falta, archivos de soporte al lado. Y tiene algo que la forma corta no aprovecha: Claude puede cargarla por su cuenta cuando la tarea que le pedís matchea su description. Un command es un solo archivo markdown en .claude/commands. Es la forma corta: un atajo que disparás vos. Las dos crean un slash command con el mismo formato, /nombre, y el nombre sale del directorio de la skill o del nombre del archivo. Si una skill y un command se llaman igual, gana la skill. La skill es la forma completa; el command, la forma de un archivo."

Dos formas, los mismos lugares

Forma Proyecto Usuario Plugins
Skill (directorio) .claude/skills/<nombre>/SKILL.md ~/.claude/skills/<nombre>/SKILL.md vía plugin instalado
Command (un archivo) .claude/commands/<nombre>.md ~/.claude/commands/<nombre>.md vía plugin instalado

Las de usuario sirven en cualquier proyecto. Las de proyecto se versionan con el repo. El demo-repo trae una de cada: la skill add-endpoint y el command pre-pr.

Al arranque entra el índice, no el procedimiento

De cada skill, al arranque entra solo su nombre y su description. El cuerpo (fases, anti-patterns) entra cuando se invoca.

  • En /context la ves listada con pocos tokens. Ese índice es lo que Claude usa para decidir si la carga por relevancia.
  • El SKILL.md completo entra cuando escribís /nombre o cuando Claude decide que la tarea matchea el description. Entra a la misma ventana: la carga se difiere, no se aísla.
  • Commands de un archivo: aparecen en el autocomplete al escribir /, y su cuerpo entra al invocarlos.

Diseño, no limitación. Con cinco skills instaladas pagás cinco descripciones cortas siempre, y el cuerpo solo de la que usás.

Leer el callout marcando la asimetría índice / cuerpo.

Anatomía de .claude/skills/add-endpoint/SKILL.md

--- name: add-endpoint description: Use when the user asks to add a new REST endpoint to the demo-repo backend. Adds the route, the schema if missing, the test, and regenerates openapi.yaml. ---
  1. Decidir method y path: confirmar con el usuario; las escrituras llevan Depends(require_bearer).
  2. Schemas: si hace falta, modelos en backend/schemas/models.py.
  3. Router: función en backend/routers/<resource>.py con response_model y status_code; método en el store si falta.
  4. Test: happy path + error esperado en tests/test_<resource>.py.
  5. OpenAPI: uv run python scripts/export_openapi.py.
  6. Verificación: uv run pytest -v pasa entero; mostrar el diff de openapi.yaml.

Anti-patterns: endpoint sin test · no regenerar openapi.yaml · endpoint sin response_model · constantes hardcodeadas que van en models.py o en una env var.

Frontmatter, seis fases, anti-patterns: arriba a abajo.

El comando /add-endpoint sale del nombre del directorio; name es solo etiqueta.

"Cuarta pregunta: cómo se usa. Abrimos la skill add-endpoint del demo-repo. Arriba, el frontmatter. El name es una etiqueta; el comando /add-endpoint sale del nombre del directorio. La description es la frase que Claude lee para decidir si la skill aplica, y sigue una convención: 'Use when X'. Una description vaga activa mal. Abajo, el cuerpo: seis fases. Decidir method y path con el usuario, y para escrituras agregar la dependency de auth. Schemas, si hacen falta modelos nuevos. Router, con response_model y status_code explícitos, y si el store no tiene la consulta, agregar el método. Tests: happy path y error esperado. Regenerar openapi.yaml con el script. Y verificar: pytest pasa entero y se muestra el diff. Al final, en rojo, los anti-patterns: lo que el agente podría hacer si nadie lo escribe. Esa lista convierte 'esperar que Claude se acuerde' en 'tenerlo escrito'."

La forma de un archivo: .claude/commands/pre-pr.md

--- description: Chequeo antes de abrir un PR (tests + openapi + diff) --- Antes de abrir un PR: 1. Corré `uv run pytest` y reportá si pasa. 2. Regenerá `openapi.yaml` con `uv run python scripts/export_openapi.py`. 3. Mostrá `git diff --stat`. No hagas commits ni push.

Once líneas, sin directorio. Crea /pre-pr igual que una skill. Para un atajo corto que disparás vos alcanza; si necesitás archivos de soporte o que Claude lo cargue por relevancia, conviene la skill.

Tres cosas que confunden de skills y commands

  • /memory, /context y /permissions no son archivos. Son built-ins del CLI: no hay skill ni command detrás que puedas abrir.
  • El description decide la activación. Si es vago, la skill entra cuando no corresponde o no entra cuando sí. La convención Use when X lo vuelve específico.
  • Una skill no es una garantía. Son instrucciones en contexto: el modelo sigue las fases con mucha más consistencia, y vos podés auditar cuál se salteó. Lo que tiene que cumplirse siempre va en settings y permisos.

El tercer bullet es el que más importa.

Skill = instrucciones en contexto; el enforcement determinístico vive en settings y permisos.

"Quinta pregunta: qué confunde. Una: /memory, /context, /permissions no son archivos. Son lógica del CLI; no hay skill ni command detrás que puedas abrir o editar. Dos: la description de la skill decide la activación. Si dice solo 'add endpoint', puede entrar en pedidos que no son de backend, o no entrar cuando sí correspondía. 'Use when the user asks to add a new REST endpoint to the demo-repo backend' es específico. Y tres, la más importante: una skill no es una garantía. Es texto que entra a la ventana, igual que CLAUDE.md. El modelo tiende a seguir las fases con mucha más consistencia que con un prompt suelto, y vos tenés un procedimiento escrito contra el cual auditar qué fase se salteó. Pero sigue siendo un LLM. Si algo tiene que cumplirse siempre, sin excepción, eso no va en una skill: va en settings y permisos, que el runtime aplica de forma determinística."

Contraste parcial:

Una skill difiere la carga de un procedimiento

Una skill empaqueta un procedimiento: fases, anti-patterns y archivos de soporte. Al arranque pagás solo su descripción; el cuerpo entra a la ventana cuando se invoca. El modelo lo sigue con mucha más consistencia, y vos podés auditar cada fase.

La skill difiere la carga dentro de la misma ventana. Un sub-agent trabaja en otra ventana: lo que explora no vuelve al padre.

Apoyar "difiere la carga" y "otra ventana".

Cierre de §11 y bridge a §12: diferir la carga vs aislar.

"Cerramos. Una skill empaqueta un procedimiento: fases, anti-patterns, archivos de soporte. Al arranque pagás solo la descripción; el cuerpo entra cuando se invoca. Y no es magia ni garantía: el modelo lo sigue con mucha más consistencia y vos tenés contra qué auditar. Pero fijate dónde entra el cuerpo: en la misma ventana. La skill difiere la carga; no aísla. Lo que sigue es la pieza que sí aísla: un sub-agent corre en otra ventana, y lo que lee para resolver la tarea no vuelve a la tuya."
