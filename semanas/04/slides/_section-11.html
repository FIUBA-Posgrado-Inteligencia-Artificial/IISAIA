Un mismo mecanismo, dos formas: skill y command

  • Skill: un directorio con SKILL.md. Empaqueta un procedimiento completo (frontmatter, fases, anti-patterns, archivos de soporte). Claude puede cargarla por su cuenta cuando la tarea matchea su description.
  • Command: un solo archivo en .claude/commands/. Es la forma corta, ideal para un atajo que disparás vos.
  • Las dos crean /nombre. El nombre sale del directorio o del archivo. Si una skill y un command se llaman igual, gana la skill.
  • → La skill es la forma completa. El command es la forma de un archivo.

Tres ítems y el callout; el tercero es el que se confunde.

Skills y commands se fusionaron: son dos formas del mismo mecanismo.

"Primera pregunta: qué es. Mucha documentación vieja las presenta como dos cosas separadas, pero hoy son el mismo mecanismo con dos formas. Una skill es un directorio con un SKILL.md adentro: empaqueta un procedimiento completo, con frontmatter, fases, anti-patterns y, si hace falta, archivos de soporte al lado. Y tiene algo que la forma corta no aprovecha: Claude puede cargarla por su cuenta cuando la tarea que le pedís matchea su description. Un command es un solo archivo markdown en .claude/commands. Es la forma corta: un atajo que disparás vos. Las dos crean un slash command con el mismo formato, /nombre, y el nombre sale del directorio de la skill o del nombre del archivo. Si una skill y un command se llaman igual, gana la skill. La skill es la forma completa; el command, la forma de un archivo."

Dos formas, los mismos lugares

Forma Proyecto Usuario Plugins
Skill (directorio) .claude/skills/<nombre>/SKILL.md ~/.claude/skills/<nombre>/SKILL.md vía plugin instalado
Command (un archivo) .claude/commands/<nombre>.md ~/.claude/commands/<nombre>.md vía plugin instalado

Las de usuario sirven en cualquier proyecto. Las de proyecto se versionan con el repo. El repo del TP trae una de cada: la skill agregar-juego y el command pre-entrega.

Mismo reparto user / proyecto que CLAUDE.md y settings.json.

"Segunda pregunta: dónde viven. Todo es markdown. La skill, en proyecto, es una carpeta dentro de .claude/skills con un SKILL.md adentro; en usuario, lo mismo bajo tu home. El command es un archivo suelto: .claude/commands/nombre.md en el proyecto, o bajo tu home. Y los dos pueden venir empaquetados en un plugin. La diferencia user versus proyecto es la misma que en CLAUDE.md y settings.json: lo de usuario viaja con vos de repo en repo; lo de proyecto se commitea y lo comparte el equipo. Al arranque entra el índice, no el procedimiento

De cada skill, al arranque entra solo su nombre y su description. El cuerpo (fases, anti-patterns) entra cuando se invoca.

  • En /context la ves listada con pocos tokens. Ese índice es lo que Claude usa para decidir si la carga por relevancia.
  • El SKILL.md completo entra cuando escribís /nombre o cuando Claude decide que la tarea matchea el description. Entra a la misma ventana: la carga se difiere, no se aísla.
  • Commands de un archivo: aparecen en el autocomplete al escribir /, y su cuerpo entra al invocarlos.

Diseño, no limitación. Con cinco skills instaladas pagás cinco descripciones cortas siempre, y el cuerpo solo de la que usás.

Leer el callout marcando la asimetría índice / cuerpo.

El cuerpo de una skill es opt-in por tarea, pero entra a la misma ventana.

"Tercera pregunta: cuándo se carga. Y es el punto que más importa de la sección. De cada skill instalada, al arranque entra solo el nombre y la description: un par de líneas, lo que Claude necesita para decidir si aplica. Las fases y los anti-patterns no entran. La skill difiere la carga; no aísla nada. Los commands de un archivo se comportan igual: aparecen en el autocomplete y su cuerpo entra cuando los invocás. Esto es diseño: con cinco skills instaladas pagás cinco descripciones cortas siempre y el cuerpo solo de la que usás. Anatomía de .claude/skills/agregar-juego/SKILL.md

--- name: agregar-juego description: Use when adding a new game to the platform — creating a Phaser scene, seeding the game in the database and wiring it to the game page. Covers the order of the steps and the verification in the browser. ---
  1. Definir el juego: slug, nombre y descripción, confirmados con el usuario. El slug aparece en cuatro lugares.
  2. Seed: la entrada en GAMES de backend/main.py; seed_games() es idempotente.
  3. La escena: frontend/js/games/<slug>.js, siguiendo la rule de escenas.
  4. Conectar la página: la entrada en GAMES de frontend/js/game-page.js.
  5. Verificar jugando: con el MCP de Playwright, jugar hasta perder y guardar un puntaje.

Anti-patterns: escribir la escena antes del seed · hacer fetch desde la escena · dar por hecho que anda porque la página no muestra errores · cambiar el slug a mitad de camino.

Frontmatter, seis fases, anti-patterns: arriba a abajo.

El comando /agregar-juego sale del nombre del directorio; name es solo etiqueta.

"Cuarta pregunta: cómo se usa. Abrimos la skill agregar-juego del repo del trabajo final. Arriba, el frontmatter. El name es una etiqueta; el comando /agregar-juego sale del nombre del directorio. La description es la frase que Claude lee para decidir si la skill aplica, y sigue una convención: 'Use when X'. Una description vaga activa mal. Abajo, el cuerpo: cinco fases, y el orden es lo que más vale. Primero definir slug, nombre y descripción, confirmados conmigo, porque el slug aparece en cuatro lugares y renombrarlo después sale caro. Segundo el seed en el backend. Tercero la escena, que sigue la rule de escenas que ya vimos. Cuarto conectar la página. Y quinto verificar jugando con el MCP de Playwright, que en este proyecto reemplaza a los tests. Al final, en rojo, los anti-patterns: escribir la escena antes del seed, hacer fetch desde la escena, o dar por terminado porque la página no muestra errores. Eso convierte 'esperar que Claude se acuerde' en 'tenerlo escrito'."

La forma de un archivo: .claude/commands/pre-entrega.md

--- description: Revisa que el TP esté en condiciones de entregarse antes de commitear --- Revisá el estado del trabajo y reportá qué está listo y qué falta. No arregles nada todavía: primero el diagnóstico. 1. `git status` y `git diff --stat`: qué cambió y qué quedó sin commitear. 2. El README es el informe: ¿algún cambio invalidó lo que narra? 3. `docs/plan.md` está congelado: avisá si aparece modificado. 4. La app levanta y la home lista los juegos.

Trece líneas, sin directorio. Crea /pre-entrega igual que una skill. Para un atajo corto que disparás vos alcanza; si necesitás archivos de soporte o que Claude lo cargue por relevancia, conviene la skill.

"Y esta es la otra forma. Punto claude, barra commands, barra pre-entrega punto md. Un archivo, trece líneas. Frontmatter con una description, que es lo que ves en el autocomplete al escribir slash. Y un cuerpo con la revisión previa a entregar: qué cambió, si el README sigue siendo cierto, si el plan congelado quedó intacto y si la app levanta. Fíjense la primera línea del cuerpo: 'no arregles nada todavía, primero el diagnóstico'. Sin eso, el agente empieza a corregir lo que encuentra y perdés la foto del estado. Crea /pre-entrega igual que una skill crea /agregar-juego. ¿Cuándo usar cada forma? Para un atajo corto que siempre disparás vos, un archivo alcanza. Cuando el procedimiento crece, necesita archivos de soporte o querés que Claude lo cargue solo cuando la tarea lo pide, pasalo a skill."

Una skill difiere la carga de un procedimiento

Una skill empaqueta un procedimiento: fases, anti-patterns y archivos de soporte. Al arranque pagás solo su descripción; el cuerpo entra a la ventana cuando se invoca. El modelo lo sigue con mucha más consistencia, y vos podés auditar cada fase.

La skill difiere la carga dentro de la misma ventana. Un sub-agent trabaja en otra ventana: lo que explora no vuelve al padre.

Apoyar "difiere la carga" y "otra ventana".

Cierre de §11 y bridge a §12: diferir la carga vs aislar.

"Cerramos. Una skill empaqueta un procedimiento: fases, anti-patterns, archivos de soporte. Al arranque pagás solo la descripción; el cuerpo entra cuando se invoca. Y no es magia ni garantía: el modelo lo sigue con mucha más consistencia y vos tenés contra qué auditar. Pero fijate dónde entra el cuerpo: en la misma ventana. La skill difiere la carga; no aísla. Lo que sigue es la pieza que sí aísla: un sub-agent corre en otra ventana, y lo que lee para resolver la tarea no vuelve a la tuya."
