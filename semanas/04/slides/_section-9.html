Config del runtime, no instrucciones para el agente

  • Archivo JSON que configura el runtime de Claude Code: el programa que envuelve al LLM.
  • No son instrucciones para el agente. Eso es CLAUDE.md y .claude/rules/. Acá van parámetros del runtime: qué modelo usar, qué environment variables pasar, qué tools puede ejecutar sin pedir confirmación.
  • CLAUDE.md dice "cómo comportarse"; settings.json dice "cómo ejecutar a Claude". Dos canales distintos hacia dos destinatarios distintos.
  • → Una instrucción textual puede ser ignorada o mal interpretada; una regla de runtime no puede.

Marcar el contraste "cómo comportarse" / "cómo ejecutar a Claude".

Propiedad central: texto para el modelo vs config para el programa que corre al modelo.

"Primera pregunta. Qué es. settings.json es un archivo JSON que configura el runtime de Claude Code: el programa que abre la sesión, carga el contexto, ejecuta las tools y le devuelve los resultados al modelo. Ese programa tiene parámetros, y viven acá. No son instrucciones para el agente; eso lo vimos en §7 y §8, Markdown que le habla al modelo. Este archivo le habla al programa: qué modelo usar, qué environment variables pasar, qué comandos puede correr sin preguntarte. CLAUDE.md dice cómo comportarse; settings.json dice cómo ejecutar a Claude. Y el callout es la razón de que exista este canal: si querés que Claude nunca haga git push, no lo escribís en CLAUDE.md, donde una instrucción puede quedar tapada por contexto posterior o reinterpretarse. Lo ponés en settings.json como regla deny, y el runtime la aplica antes de que Claude llegue a intentarlo."

Cinco niveles, de mayor a menor precedencia

Nivel 1 Managed
lo instala un admin de la organización Fija el techo: lo que define no se pisa desde ningún nivel de abajo.
Nivel 2 Línea de comandos

Nivel 3 Local
.claude/settings.local.json · en .gitignore Tu override personal en este repo. No se versiona.
Nivel 4 Proyecto
.claude/settings.json · commiteado Config compartida: la ve todo el que clona el repo.
Nivel 5 Usuario
~/.claude/settings.json Tus defaults, en todos tus repos. No los ve el equipo.

Listas de permissions (allow, deny, ask): se suman entre niveles.

"Segunda pregunta. Dónde vive. Cinco niveles, de mayor a menor precedencia. Managed lo instala un admin en organizaciones grandes y fija el techo; en un proyecto personal no aparece. Después, los flags de la línea de comandos: claude --model haiku vale solo para esa ejecución. Local, en .claude/settings.local.json: tu override personal para este repo, y va al .gitignore siempre. Proyecto, en .claude/settings.json, commiteado: lo que comparte el equipo. Usuario, en tu home: tus defaults, que te siguen a todos los repos. Y la regla de combinación tiene dos partes. Para valores escalares, como model o una variable de env, gana el nivel más alto: si el proyecto dice sonnet y tu usuario dice haiku, corre sonnet. Para las listas de permissions no hay pisada: se suman. Si tu local agrega un allow, no borra los deny del proyecto."

No leer los tres archivos: marcar la cascada común y la condición de confianza de Codex.

El archivo de configuración del runtime existe en los tres, con formato distinto y la misma idea de niveles.

"La configuración del runtime también existe en los otros dos. Codex usa TOML, config.toml, con uno de usuario en su carpeta y uno de proyecto, con una condición que Claude Code no tiene: el de proyecto solo se carga si marcaste ese repo como confiable. Tiene sentido, porque un repo que clonás podría traer una config que le da más permisos al agente. OpenCode usa opencode.json, que acepta comentarios, mergea el global con el del proyecto y deja referenciar variables de entorno o archivos adentro de los valores, útil para no escribir una API key en el archivo. Tres formatos, pero la misma estructura: niveles, y el más específico pisa al más general."

Seis campos típicos del archivo

Campo Qué controla
model Modelo de la sesión. Acepta alias: "sonnet", "opus", "haiku".
env Environment variables para los procesos que lanza Claude (servidor, tests, scripts).
permissions Reglas allow / deny / ask por tool, y el modo de arranque en defaultMode.
hooks Scripts que corren ante eventos del runtime: antes o después de una tool call, al arrancar la sesión.
attribution Cambia u oculta la atribución a Claude en commits ("commit") y PRs ("pr").
cleanupPeriodDays Cuántos días se guardan los transcripts locales de las sesiones.

Recorrer sin leer todo; detenerse en permissions.

Seis campos típicos; permissions resaltado porque tiene sección propia.

"Cuarta pregunta. Cómo se usa. Seis campos típicos. model define el modelo de la sesión y acepta alias como sonnet, opus o haiku, así no dependés del nombre completo de la versión. env son environment variables para los procesos que lanza Claude: cuando corre uvicorn o pytest, esas variables están ahí. permissions es el campo resaltado: las listas allow, deny y ask, y adentro también defaultMode, el modo con el que arranca la sesión. Lo vemos completo en §10. hooks son scripts que el runtime dispara ante eventos, como antes de una tool call o al arrancar la sesión; los nombramos y seguimos. attribution controla la línea de atribución a Claude en commits y PRs; reemplaza a includeCoAuthoredBy, que quizás encuentren en ejemplos viejos. Y cleanupPeriodDays, cuántos días se guardan los transcripts locales."

El settings.json del repo

.claude/settings.json
  • "model": "sonnet" · todo el que abre el repo trabaja con el mismo modelo. Tu settings.local.json puede pisarlo en tu máquina; es lo que muestra el .example.
  • "attribution": { "pr": "" } · los PRs que abre Claude salen sin línea de atribución.
  • "cleanupPeriodDays": 30 · un mes de transcripts locales.
  • "permissions" · 7 reglas allow, 4 deny, 2 ask.
  • No hay "env" · este proyecto no usa variables de entorno. Un campo que no aplica no se pone "por las dudas": cada línea de acá tiene que estar por una razón.

Detenerse en model: el proyecto propone, tu local dispone.

Los campos top del archivo real; el bloque permissions se abre en §10.

"Vamos al archivo real del repo del trabajo final. model en sonnet: el que abra el repo trabaja con ese modelo, salvo que su settings.local.json diga otra cosa; el .example que viene en el repo pone haiku, justamente para mostrar que el local pisa al proyecto. attribution con pr vacío: los PRs que abra Claude no llevan la línea de atribución. cleanupPeriodDays en treinta. Y permissions: siete reglas allow, cuatro deny, dos ask; ese bloque lo abrimos entero en la sección que sigue. Y miren lo que no está: no hay env, porque este proyecto no usa variables de entorno. Suena obvio, pero es una decisión: un archivo de configuración se llena de campos copiados de tutoriales, y cada línea que no tiene razón de ser es una línea que alguien va a interpretar mal después."

Parámetros del programa, aplicados sin interpretación

settings.json configura el runtime de Claude Code, no al agente: qué modelo corre, qué environment variables reciben los procesos, qué hooks se disparan y qué tools se ejecutan sin preguntarte. Una regla de runtime es determinística: no se ignora ni se reinterpreta.

El campo con más consecuencias es permissions. La diferencia entre un agente que puede hacer git push y uno que tiene prohibido intentarlo es una línea de deny.

Apoyar "runtime" y "determinística".

Tres listas, un orden de evaluación y varias sutilezas: le dedicamos la sección que sigue."
