Anclaje visual: el mismo diagrama del §3, ahora con foco en los servers. Las tres primitives viven adentro de cada server. La fila de abajo es preview de los tres slides que siguen.

"Volvemos al diagrama. El host y los clientes se atenúan, los servers se destacan. Lo que importa ahora es qué expone cada server por adentro: la doc de MCP define tres primitives del lado del server, y la clave para entenderlas es el framing oficial: cada una tiene un dueño distinto de la iniciativa, alguien que decide cuándo se usa. Tools las invoca el modelo, resources las decide cargar la aplicación, prompts las pide el usuario. Esa diferencia organiza todo. Vamos una por una, y después vemos qué pone el cliente del otro lado."

Tools.

primitive 1 — model-controlled

Funciones que el LLM puede invocar. El cliente las descubre primero, después el modelo decide cuál llamar. Ejemplo: Playwright MCP.

1
tools/list
↳
catálogo que devuelve el server — cada tool con nombre, descripción e inputSchema
browser_navigate inputs: url: string (required)
"Navigate to a URL"
browser_click inputs: target: string (required), element: string (opcional)
"Perform click on a web page"
2
tools/call(name: "browser_navigate", arguments: { url: "https://docs.anthropic.com" })
↳
el server ejecuta y devuelve
{ content: [ { type: "text", text: "Navigated to docs.anthropic.com — page snapshot..." } ] }
así se ve en Claude Code
> Abrí docs.anthropic.com y dame los headers principales
→ tool call: browser_navigate({ url: "https://docs.anthropic.com" })
Allow mcp__playwright__browser_navigate? (y/n)
approved · result returned to model
claude > Los headers principales son: Introduction, Quickstart, Models, Guides, API Reference...

Tres reveals — discover, invoke, CC interaction.

Tools como flujo de 2 pasos con schema completo + cierre concreto que muestra cómo se ve en Claude Code. La confirmación antes de ejecutar visualiza el "acción con efecto" sin necesidad de etiquetarlo. Params y descripciones verificados contra github.com/microsoft/playwright-mcp (README, sección de tools): browser_click pide target (required) y element (opcional, solo para el permiso); browser_navigate sin cambios de fondo.

"Primera primitive: tools. Funciones que el LLM puede invocar. Para el ejemplo uso Playwright MCP — el server real de Microsoft que ya van a ver en el demo del §7."

"Paso uno. El cliente le pregunta al server qué tools tiene, con un tools/list. El server le devuelve un catálogo — esos dos ejemplos son dos tools reales de Playwright MCP: navegar a una URL y hacer click en un elemento. Cada entry trae el nombre, una descripción que el modelo va a leer, y un schema de parámetros — noten que browser_click pide un target exacto, la referencia del snapshot, y element es opcional, solo para mostrarle al usuario qué va a tocar."

"Paso dos. Durante la conversación, cuando el modelo decide que tiene que abrir la doc de Anthropic, mira el catálogo, identifica browser_navigate, arma los argumentos concretos con la URL, y emite un tools/call. El server real abre el browser headless, navega a esa URL y devuelve el snapshot de la página al modelo."

"Y así se ve esto desde Claude Code. El usuario pide algo en lenguaje natural — 'abrí docs.anthropic.com y dame los headers'. Claude identifica que tiene que usar browser_navigate y arma el call. Pero antes de ejecutar, Claude Code pide confirmación con el nombre completo de la tool, mcp__playwright__browser_navigate — porque los tools cambian el mundo, son acción con efecto. Una vez aprobado, el server ejecuta y la respuesta vuelve. El modelo después la usa para contestar."

Resources.

primitive 2 — application-controlled

Datos pasivos accesibles por URI. La aplicación los descubre y decide cuáles cargar al contexto. Ejemplo: un MCP server de Postgres — expone el schema de cada tabla.

1
resources/list
↳
catálogo — cada resource con uri, name, mimeType
postgres://db-prod/users/schema mimeType: application/json
name: "users.schema" · description: "Schema for users table"
postgres://db-prod/orders/schema mimeType: application/json
name: "orders.schema" · description: "Schema for orders table"
2
resources/read(uri: "postgres://db-prod/users/schema")
↳
el server consulta la base y devuelve
{ contents: [ { uri: "postgres://db-prod/users/schema", mimeType: "application/json", text: '{ "columns": [{ "name": "id", "type": "uuid" }, { "name": "email", "type": "text" }, ...] }' } ] }
así se ve en Claude Code
[ el usuario adjunta @postgres:postgres://db-prod/users/schema y @postgres:postgres://db-prod/orders/schema al prompt ]
→ Claude Code lee esos resources con ReadMcpResourceTool y los carga al contexto antes de llamar al modelo
> Escribime una query que traiga usuarios con pedidos sin pagar
claude > SELECT u.id, u.email FROM users u JOIN orders o ON o.user_id = u.id WHERE o.status = 'unpaid' — columnas reales, sin alucinarlas

Tres reveals — discover, invoke, CC interaction.

Resources con un server de Postgres genérico (el server de referencia que documentaba esto quedó archivado, así que no se nombra como "oficial"). CC ya lee archivos nativamente, pero no se conecta solo a una DB para introspeccionar schemas — ahí entra el resource. Cronología clave: el read sucede ANTES de que el usuario pregunte algo. En Claude Code la vía de attach es @server:uri (code.claude.com/docs/en/mcp.md); el modelo también puede leer resources directo con ReadMcpResourceTool, sin pasar por el usuario.

"Segunda primitive: resources. Datos pasivos accesibles por URI. Ejemplo: un MCP server de Postgres que expone el schema de cada tabla de la base como un resource — algo que CC no puede hacer solo, porque no se conecta a una base de datos para introspeccionar schemas."

"Paso uno. El cliente le pide al server el catálogo con resources/list. El server introspecciona la base — corre las queries de catálogo de Postgres — y devuelve una URI por cada tabla. Dos ejemplos: users.schema y orders.schema. Cada URI viene con mimeType application slash json porque el contenido es JSON estructurado del schema."

"Paso dos. La app decide cargar el schema de users. Emite resources/read con la URI concreta. El server consulta la base y devuelve el JSON del schema: las columnas, tipos, nullability, índices. La app lo inyecta al contexto del modelo."

"Y así se ve en Claude Code, con la cronología correcta: el usuario adjunta los schemas de users y orders con la sintaxis arroba-server-dos puntos-uri, @postgres:postgres://db-prod/users/schema. Es una acción del usuario en el prompt, no una consulta al modelo. Claude Code lee esos resources con ReadMcpResourceTool y los carga al contexto antes de que el usuario pregunte nada. Recién después llega la pregunta: escribime una query que traiga usuarios con pedidos sin pagar. El modelo arma el SQL con los nombres reales de las columnas — sin alucinarlos, porque los tiene en contexto. Eso es application-controlled. Nota al margen: algunos servers exponen resource templates, URIs parametrizadas con placeholders entre llaves, que la app expande con valores concretos en tiempo real."

Prompts.

primitive 3 — user-controlled

Templates reutilizables. El usuario los descubre y los invoca explícitamente con argumentos. Ejemplo genérico: un server de code review podría exponer esto.

1
prompts/list
↳
catálogo — cada prompt con nombre, descripción y arguments
review-pr arguments: diff: string (required)
"Review a pull request diff with structured feedback"
explain-commit arguments: sha: string (required)
"Explain what a commit changes and why"
2
prompts/get(name: "explain-commit", arguments: { sha: "a3f9c21" })
↳
el server expande el template y devuelve
{ messages: [ { role: "user", content: { type: "text", text: "Explain what commit a3f9c21 changes and why..." } } ] }
así se ve en Claude Code
> /mcp__code-review__explain-commit a3f9c21
→ Claude Code llama prompts/get("explain-commit", { sha: "a3f9c21" })
→ template expandido, mensaje listo enviado al modelo
claude > El commit a3f9c21 refactoriza el manejo de errores en auth.ts, sin cambiar la lógica pública.

Tres reveals — discover, invoke, CC interaction.

Prompts como flujo de 2 pasos + cierre concreto que muestra la sintaxis real de slash command que el usuario tipea (/mcp__server__prompt, args separados por espacio — code.claude.com/docs/en/mcp.md). El ejemplo de server es explícitamente genérico, no un producto real, para no inventar un "Git MCP" que no existe así.

"Tercera primitive: prompts. Templates reutilizables. El ejemplo es genérico a propósito: pensemos en un server de code review cualquiera, de los que ya existen en la comunidad para acciones recurrentes sobre un repositorio."

"Paso uno. El cliente le pide al server qué templates tiene disponibles con prompts/list. El server le devuelve un catálogo: review-pr para revisar un pull request, explain-commit para entender qué hace un commit concreto. Cada template tiene un nombre, una descripción, y un schema de argumentos."

"Paso dos. El usuario decide pedirle al agente que explique un commit puntual. El host emite prompts/get con el nombre y el sha. El server combina internamente instrucciones para el modelo con ese dato, y devuelve todo armado como un mensaje listo en la estructura messages que ven en la response. No ejecuta nada, sólo arma el material."

"Y así se ve en Claude Code, con la sintaxis real: barra, mcp doble guión bajo nombre del server doble guión bajo nombre del prompt, y los argumentos separados por espacio — barra mcp__code-review__explain-commit a3f9c21. Si tipean barra solita y tienen un server MCP conectado, sus prompts aparecen ahí mezclados con los comandos nativos. Claude Code llama prompts/get internamente, el template se expande, se envía al modelo. Por eso user-controlled — el usuario invoca explícitamente, no se disparan solos."

Por qué la separación.

Cada primitive tiene un dueño distinto de la iniciativa. Eso determina todo lo demás.

Primitive
Quién decide
Permisos
Interfaz típica
tools
El modelo
De acción, con confirmación
Diálogo de confirmación
resources
La aplicación
De lectura, transparentes
Carga automática / picker
prompts
El usuario
Invocación explícita
Slash commands

Iniciativa distinta → permisos distintos → UI distinta. Mezclarlas haría imposible un modelo coherente.

Síntesis: el por qué pedagógico de las tres primitives. La diferencia de iniciativa determina permisos y UI. Esa es la razón estructural por la que MCP las separa.

"La síntesis. Por qué tres primitives distintas y no una sola con flags. La razón es que cada una tiene un dueño distinto de la iniciativa, y esa diferencia se propaga al resto del diseño. Los tools los decide el modelo, y eso implica un modelo de permisos de acción con confirmación. Los resources los decide la aplicación, eso implica permisos de lectura, transparentes, sin pedir nada. Los prompts los decide el usuario, eso implica invocación explícita, slash commands. Iniciativa distinta lleva a permisos distintos lleva a interfaz distinta: mezclar las tres en una sola primitive haría imposible un modelo de permisos coherente, porque el host no sabría cuándo pedir confirmación, cuándo cargar transparente, cuándo esperar al usuario. Por eso la spec separa."

Y del otro lado: lo que pone el cliente.

El cliente también expone primitives hacia el server. La comunicación no es de una sola dirección.

la que queda activa

Elicitation

El server necesita un dato que no tiene y no puede seguir sin él — confirmación, preferencia, valor faltante. Devuelve resultType: "input_required" con la pregunta; el cliente se la hace al usuario y reintenta el pedido original con la respuesta.

Roots

deprecada — spec 2026-07-28

Reemplazo: directorios por parámetro de tool, URI de resource o config del server.

Sampling

deprecada — spec 2026-07-28

Reemplazo: integrar el LLM directo contra la API del provider.

Logging

deprecada — spec 2026-07-28

Reemplazo: stderr (stdio) u OpenTelemetry.

Siguen funcionando durante la ventana de deprecación — doce meses como mínimo — pero no conviene construir nada nuevo sobre ellas.

Cierre de §4: client primitives, al día con SEP-2577 (modelcontextprotocol.io/specification/latest/changelog). Elicitation es la única vigente, vía multi round-trip requests (resultType input_required, el cliente reintenta con inputResponses). Roots, Sampling y Logging quedan grises con su reemplazo en una línea, sin profundizar.

"Y del otro lado: el cliente también expone primitives hacia el server, la comunicación no es de una sola dirección. De las cuatro que define la spec, hoy conviene mirar solo una en detalle: Elicitation. El server la usa cuando necesita un dato que no tiene y no puede seguir sin él — una confirmación, una preferencia, un valor faltante a mitad de una operación. En la spec actual esto ya no es un mensaje aparte: el server devuelve un resultado con input_required y la pregunta adentro, el cliente se la hace al usuario, y reintenta el pedido original con la respuesta. Las otras tres — Roots, Sampling, Logging — siguen ahí, el server que las use todavía funciona, pero están en ventana de deprecación: no construyan nada nuevo pensando en ellas. Roots se reemplaza pasando el directorio como parámetro de una tool o en la config del server. Sampling se reemplaza integrando el LLM directo contra la API del provider, sin pedírselo al cliente. Logging se reemplaza mandando a stderr si el transport es stdio, o con OpenTelemetry."
