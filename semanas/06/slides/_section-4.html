"Volvemos al diagrama. El host y los clientes se atenúan, los servers se destacan. Lo que importa ahora es qué expone cada server por adentro: la doc de MCP define tres primitives del lado del server, y la clave para entenderlas es el framing oficial: cada una tiene un dueño distinto de la iniciativa, alguien que decide cuándo se usa. Tools las invoca el modelo, resources las decide cargar la aplicación, prompts las pide el usuario. Esa diferencia organiza todo. Vamos una por una, con un mismo server de ejemplo para las tres."

Un server, tres primitives.

Un server MCP de clima, completo en un archivo de Python. Lo vamos a usar de ejemplo para las tres.


from mcp.server import MCPServer

mcp = MCPServer("clima")

@mcp.tool()
def clima_actual(ciudad: str) -> str:
    """Devuelve el clima actual de una ciudad."""
    ...  # consulta Open-Meteo

@mcp.resource("clima://pronostico/{ciudad}")
def pronostico(ciudad: str) -> str:
    """Pronóstico de los próximos 3 días."""
    ...

@mcp.prompt()
def reporte_clima(ciudad: str) -> str:
    """Arma un reporte del clima de una ciudad."""
    return f"Usá la tool clima_actual para {ciudad}..."

mcp.run()  # stdio

Una primitive es una función con un decorador. El SDK arma el schema con los type hints y el docstring.

Cuatro clicks — tool, resource, prompt, plomería.

Server real, vive en semanas/06/demo-clima/server.py (SDK oficial de Python, mcp 2.x, datos de Open-Meteo sin API key). El código del slide está recortado: el archivo real tiene además el resource fijo clima://ciudades y el llamado HTTP. Las tres slides que siguen usan este mismo server, con las respuestas JSON capturadas de verdad.

"Antes de ir una por una, les muestro un server entero. Es un server MCP de clima, lo escribí para la clase, y es esto: un archivo de Python. Lo van a ver en las tres slides que siguen, así que vale mirarlo una vez completo."

"Primero, una tool: clima_actual. Es una función común que recibe una ciudad y devuelve un string con el clima. Lo único MCP es el decorador arroba mcp punto tool."

"Después, un resource. Mismo patrón, otro decorador, y acá aparece la URI: clima dos puntos barra barra pronostico, con la ciudad entre llaves. Eso es un template — la URI tiene un hueco que se completa con la ciudad que pidas."

"Y un prompt: reporte_clima. Fíjense que no consulta nada, solo devuelve texto — un mensaje armado para el modelo. Eso va a importar cuando lo veamos."

"El resto es plomería: le ponés nombre al server y lo corrés. Sin argumentos corre por stdio, el transport local que vimos en la sección anterior. No escribieron ni un schema ni una línea de JSON-RPC: el SDK lee los type hints y el docstring y arma todo lo que el cliente va a descubrir."

Tools.

primitive 1 — model-controlled

Funciones que el LLM puede invocar. El cliente las descubre primero, después el modelo decide cuál llamar. En el server de clima: clima_actual.

1
tools/list
↳
catálogo que devuelve el server — cada tool con nombre, descripción e inputSchema
clima_actual inputs: ciudad: string (required)
"Devuelve el clima actual de una ciudad: temperatura, viento y estado del cielo."
2
tools/call(name: "clima_actual", arguments: { ciudad: "Montevideo" })
↳
el server consulta Open-Meteo y devuelve
{ content: [ { type: "text", text: "Montevideo, Uruguay: 17.7 °C, viento 15.3 km/h, tormenta." } ] }
así se ve en Claude Code
> ¿Qué temperatura hace en Montevideo?
→ tool call: clima_actual({ ciudad: "Montevideo" })
Allow mcp__clima__clima_actual? (y/n)
approved · result returned to model
claude > En Montevideo hay 17.7 °C, con tormenta y viento de 15 km/h. Si salís, llevá paraguas.

Tres reveals — discover, invoke, CC interaction.

Tools con el server de clima del slide anterior. El catálogo y la respuesta son los JSON reales del server (capturados con un cliente MCP por stdio), recortados a lo que importa. El nombre en el permiso sigue la regla de Claude Code: mcp__server__tool. La confirmación antes de ejecutar visualiza el "acción con efecto" sin necesidad de etiquetarlo.

"Primera primitive: tools. Funciones que el LLM puede invocar. Seguimos con el server de clima: su tool es clima_actual."

"Paso uno. El cliente le pregunta al server qué tools tiene, con un tools/list. El server devuelve el catálogo — acá hay una sola tool. Fíjense de dónde sale cada campo: el nombre es el de la función, la descripción es el docstring, y el schema dice que ciudad es un string obligatorio porque así lo dice el type hint. Nadie escribió eso a mano. La descripción es lo que el modelo lee para decidir cuándo usarla."

"Paso dos. Durante la conversación, cuando el modelo decide que necesita el clima de Montevideo, mira el catálogo, elige clima_actual, arma los argumentos y emite un tools/call. El server corre la función — que consulta Open-Meteo — y devuelve el resultado como texto."

"Y así se ve desde Claude Code. El usuario pregunta en lenguaje natural, sin nombrar ninguna tool. Claude decide usar clima_actual y arma el call. Antes de ejecutar, Claude Code pide permiso con el nombre completo: mcp, doble guión bajo, clima — el nombre del server —, doble guión bajo, clima_actual. Los tools pueden cambiar el mundo, por eso se confirman. Aprobado, el server ejecuta y el modelo contesta con el dato. Eso es model-controlled: la iniciativa la tuvo el modelo."

Resources.

primitive 2 — application-controlled

Datos pasivos accesibles por URI. El cliente los descubre; la aplicación decide cuáles cargar al contexto. En el server de clima: el pronóstico de una ciudad.

1
resources/list · resources/templates/list
↳
catálogo — resources fijos y templates con parámetro, cada uno con uri, name, mimeType
clima://ciudades mimeType: text/plain
name: "ciudades" · description: "Ciudades sugeridas para la demo."
clima://pronostico/{ciudad} template · mimeType: text/plain
name: "pronostico" · description: "Pronóstico de los próximos 3 días para una ciudad."
2
resources/read(uri: "clima://pronostico/Madrid")
↳
el server completa el template, consulta Open-Meteo y devuelve
{ contents: [ { uri: "clima://pronostico/Madrid", mimeType: "text/plain", text: "Pronóstico para Madrid:\n2026-10-07: 14.0–21.7 °C, tormenta\n2026-10-08: 13.1–20.0 °C, nublado\n..." } ] }
así se ve en Claude Code
[ el usuario adjunta @clima:clima://pronostico/Madrid al prompt ]
→ Claude Code le pide el resource al server (resources/read) y lo adjunta al contexto antes de llamar al modelo
> Viajo a Madrid mañana, ¿qué llevo?
claude > Mañana en Madrid va de 13 a 20 °C y nublado: capas y un abrigo liviano para la mañana.

Tres reveals — discover, invoke, CC interaction.

Resources con el mismo server de clima. Catálogo y respuesta son los JSON reales, recortados. Los resources fijos salen de resources/list y los templates de resources/templates/list — por eso el paso 1 muestra los dos. Cronología clave: el read sucede ANTES de que el modelo vea la pregunta. En Claude Code la vía de attach es @server:uri (code.claude.com/docs/en/mcp): el cliente pide el resource con resources/read y lo adjunta al contexto. Escribir la URI del template a mano, con la ciudad completada, funciona (probado). La doc también dice que Claude Code le da al modelo tools para listar y leer resources por su cuenta; no nombra esas tools, así que no las nombres.

"Segunda primitive: resources. Datos pasivos accesibles por URI. No hacen nada, se leen. En el server de clima, el pronóstico de una ciudad."

"Paso uno. El cliente pide el catálogo. Acá hay dos cosas: un resource fijo, la lista de ciudades, con su URI clima://ciudades; y un template, el pronóstico, que tiene la ciudad entre llaves. El template es una URI con un hueco: el server no puede listar el pronóstico de todas las ciudades del mundo, entonces publica el patrón y vos lo completás."

"Paso dos. La app decide cargar el pronóstico de Madrid: completa el template y emite resources/read con la URI concreta. El server consulta Open-Meteo y devuelve el texto con los próximos tres días. La app lo inyecta al contexto del modelo."

"Y así se ve en Claude Code, con la cronología correcta. El usuario adjunta el pronóstico con arroba, igual que adjunta un archivo: arroba, clima — el server —, dos puntos, y la URI. Es una acción del usuario en el prompt, no una decisión del modelo. Claude Code pide el resource y lo adjunta antes de que el modelo vea nada. Recién ahí llega la pregunta, y el modelo contesta con los números del pronóstico porque ya los tiene en contexto. No llamó a ninguna tool. Eso es application-controlled."

Prompts.

primitive 3 — user-controlled

Templates reutilizables. El cliente los lista; el usuario elige cuál invocar, con argumentos. En el server de clima: reporte_clima.

1
prompts/list
↳
catálogo — cada prompt con nombre, descripción y arguments
reporte_clima arguments: ciudad (required)
"Arma un reporte del clima de una ciudad, con recomendación de qué ponerse."
2
prompts/get(name: "reporte_clima", arguments: { ciudad: "Buenos_Aires" })
↳
el server expande el template y devuelve
{ messages: [ { role: "user", content: { type: "text", text: "Usá la tool clima_actual para consultar el clima de Buenos Aires. Después escribí un reporte de tres líneas..." } } ] }
así se ve en Claude Code
> /mcp__clima__reporte_clima Buenos_Aires
→ Claude Code llama prompts/get y le manda al modelo el mensaje armado
→ el modelo sigue la instrucción: tool call clima_actual({ ciudad: "Buenos Aires" })
claude > Buenos Aires: 16 °C y tormenta. Campera impermeable. Sí, llevá paraguas.

Tres reveals — discover, invoke, CC interaction.

Prompts con el mismo server de clima. Catálogo y messages son los JSON reales, recortados. Sintaxis de Claude Code verificada en code.claude.com/docs/en/mcp: en el menú / aparece como /clima:reporte_clima (MCP), y tipear /mcp__clima__reporte_clima también lo corre. Los argumentos se separan por espacios, por eso "Buenos_Aires" va con guión bajo (el server lo convierte). El cierre muestra que las primitives se combinan: el prompt no ejecuta nada, pero el mensaje que arma le pide al modelo usar la tool.

"Tercera primitive: prompts. Templates reutilizables. En el server de clima: reporte_clima, un reporte con recomendación de qué ponerse."

"Paso uno. El cliente pide los templates disponibles con prompts/list. El server devuelve el catálogo: el nombre, la descripción, y los argumentos — acá uno solo, la ciudad, obligatorio."

"Paso dos. El usuario elige el prompt y le pasa la ciudad. El host emite prompts/get con el nombre y el argumento. El server completa el template y devuelve un mensaje listo, en la estructura messages que ven ahí. No consultó el clima, no ejecutó nada: solo armó el texto. Fíjense qué dice ese texto — le pide al modelo que use la tool clima_actual."

"Y así se ve en Claude Code. Si tipean barra con el server conectado, el prompt aparece en el menú mezclado con los comandos nativos. Lo corren con barra, mcp, doble guión bajo, clima, doble guión bajo, reporte_clima, y la ciudad separada por espacio — con guión bajo en Buenos_Aires, porque cada argumento es una sola palabra. Claude Code llama prompts/get y le manda al modelo el mensaje armado. Y ahora el modelo sí llama la tool, porque el mensaje se lo pidió. User-controlled: la iniciativa fue del usuario. Y de paso ven que las primitives se combinan: un prompt que dispara una tool."

Por qué la separación.

Cada primitive tiene un dueño distinto de la iniciativa. Eso determina todo lo demás.

Primitive
Quién decide
Permisos
Interfaz típica
tools
El modelo
De acción, con confirmación
Diálogo de confirmación
resources
La aplicación
De lectura, transparentes
Carga automática / picker
prompts
El usuario
Invocación explícita
Slash commands

Iniciativa distinta → permisos distintos → UI distinta. Mezclarlas haría imposible un modelo coherente.

Síntesis: el por qué pedagógico de las tres primitives. La diferencia de iniciativa determina permisos y UI. Esa es la razón estructural por la que MCP las separa.

"La síntesis. Por qué tres primitives distintas y no una sola con flags. La razón es que cada una tiene un dueño distinto de la iniciativa, y esa diferencia se propaga al resto del diseño. Los tools los decide el modelo, y eso implica un modelo de permisos de acción con confirmación. Los resources los decide la aplicación, eso implica permisos de lectura, transparentes, sin pedir nada. Los prompts los decide el usuario, eso implica invocación explícita, slash commands. Iniciativa distinta lleva a permisos distintos lleva a interfaz distinta: mezclar las tres en una sola primitive haría imposible un modelo de permisos coherente, porque el host no sabría cuándo pedir confirmación, cuándo cargar transparente, cuándo esperar al usuario. Por eso la spec separa."
