Cuatro reveals — el aterrizaje y una capacidad faltante por card.

El alumno aterriza tres casos concretos que cualquiera vivió. Cada card tiene el pedido en mono (lo que vos querrías escribir) y por qué el set actual no lo cubre limpio. El tercero anticipa el demo de §8: la razón por la que no está no es memoria del modelo, es que no hay canal hacia ese servicio. Browser: con la extensión Claude in Chrome (plan Pro/Max/Team/Enterprise y login) sí se puede controlar un browser real desde Claude Code — por dentro, esa extensión es un MCP server (aparece como claude-in-chrome en /mcp). Playwright sigue siendo la opción portable, sin plan ni login.

"Tres ejemplos concretos de capacidad que el set por default no te da."

"Primero: querés tirar una query contra Postgres de producción y traerte filas que matchean un patrón. Bash con psql te lo permite si las credenciales están en el entorno. Pero el agente no sabe el schema, no sabe los tipos, no sabe qué columnas son sensibles. Querrías un tool con tipos declarados y permisos, no una shell ciega."

"Segundo: querés controlar un browser. Abrir una página, hacer click, sacar una screenshot, completar un form. Bash con curl no hace nada de eso — no renderiza, no ejecuta JS, no clickea. La capacidad no está, de fábrica."

"Tercero: querés que el agente toque tu gestor de tareas — Linear, Jira. Marcar un ticket, asignarlo, agregar un comentario. Bash no tiene ni el cliente HTTP armado para ese API ni el token a mano. Tres situaciones reales. Tres cosas que el agente, con el set actual, no puede. ¿Qué hacés?"

¿Cómo le damos Postgres al agente?

1

El runtime ya corre psql.

$ psql postgresql://readonly@10.0.1.42/analytics \
    -c "SELECT email FROM users LIMIT 5"

Funciona — mientras lo que Opus sabe de psql cubra lo que necesitás.

2

Agregás instrucciones al contexto.

# CLAUDE.md
Conexión: postgresql://readonly@10.0.1.42/analytics
Schema: users(id, email, signup_date, active)

Mejor. Pero no sabés lo que no sabés que falta.

3

Sumás rules y permisos para que no haga DELETE.

{
  "permissions": {
    "deny": ["Bash(psql*DELETE*)",
      "Bash(psql*UPDATE*)", "Bash(psql*DROP*)"]
  }
}

El deny bloquea el comando, sin preguntar. Para Claude Code.

Cuatro reveals — el viaje real del dev.

Escenario concreto: vos sos un dev usando Claude Code con Opus, querés trabajar contra una base Postgres. Vas iterando con las herramientas que ya conocés de S04/S05 — Bash, CLAUDE.md, rules, settings — y descubrís que el problema estructural aparece cuando querés moverte a otro runtime.

"Ahora vamos al escenario real. Ustedes están usando Claude Code con Opus, y quieren que el agente trabaje contra una base de Postgres. ¿Cómo lo van resolviendo, paso a paso? Todo lo que vamos a ver son herramientas que ya conocen de las últimas dos clases."

"Paso uno. Lo más simple: el runtime ya tiene Bash, y Opus sabe algo de psql del entrenamiento. Le tiran un pedido, el agente arma una query psql y la ejecuta. Funciona — mientras lo que Opus sabe sobre psql cubra lo que ustedes necesitan. Si Opus se olvidó del flag para timestamps con timezone, o no conoce la convención que usa el equipo, ahí estás. Están a la merced de los pesos del modelo."

"Paso dos. Quieren más control. Agregan instrucciones al contexto — un CLAUDE.md con detalles de la base, el schema, las convenciones del equipo. Mejor. Pero acá aparece un problema sutil: cómo saben que no les falta nada. La doc la escriben ustedes, y ustedes no saben lo que no saben. Cada vacío en esa doc es un riesgo de que el agente actúe mal porque le falta información."

"Paso tres. Suman reglas y permisos. Configurás el settings.json de Claude Code con un deny que bloquea directo cualquier DELETE, UPDATE o DROP contra la base — no es que el agente pida confirmación, el comando directamente no corre. Agregás hooks que validen otros comandos antes de ejecutarse. El setup ya funciona bien. Para Claude Code."

"Paso cuatro. Y acá está la trampa estructural. Mañana querés probar Cursor — mismo agente, otro runtime. Tu CLAUDE.md no se llama CLAUDE.md ahí, las rules viven en .cursor/rules/. Tu settings.json no tiene equivalente directo, hay otra forma de configurar permisos. Tus hooks viven en otro lado. Codex CLI tiene su propio formato — AGENTS.md, config.toml. OpenCode también — AGENTS.md, opencode.json. Cada runtime tiene su propia forma de implementar lo mismo. Y por cada capacidad nueva — browser, tu gestor de tareas, lo que sea — multiplicás el trabajo otra vez. La pregunta que sigue: ¿por qué crece tan feo?"

Un reveal — N×M visible primero, después aparece N+M al lado.

Convergencia visual del §1: cada celda de la matriz es lo que el dev acaba de armar para Postgres en Claude Code — el CLAUDE.md + las rules + los permisos. Cuatro capacidades por cuatro runtimes = dieciséis setups custom. Un protocolo común lo colapsa a N + M.

"Acá está la convergencia. Miren el grid de la izquierda. Cada celda es lo que ustedes acaban de armar para Postgres en Claude Code — el CLAUDE.md con instrucciones, las rules con permisos, los hooks. Cuatro capacidades por cuatro runtimes. Postgres en Claude Code, un setup. Postgres en Cursor, otro setup. Postgres en Codex CLI, otro. Postgres en OpenCode, otro. Y así con browser, con tareas, con Slack. Cuatro por cuatro: dieciséis setups completos, cada uno con sus formatos. Si mañana aparece un runtime nuevo, cuatro setups más. Si aparece una capacidad nueva, otros cuatro. Esto crece feo. Esto es N por M."

"Si en cambio metés un protocolo común al medio — esto es lo que aparece a la derecha — la matriz se colapsa. Cada capacidad habla el protocolo una sola vez. Cada runtime entiende el protocolo una sola vez. Cuatro más cuatro: ocho conexiones. Runtime nuevo: una integración, hereda todas las capacidades. Capacidad nueva: una integración, queda disponible en todos los runtimes. La matriz desaparece. Esto es N más M. Y ese protocolo común tiene nombre — viene ahora."

La salida estructural

MCP

Un protocolo común que hosts y proveedores de capacidades hablan por igual.

Bridge al resto del bloque. El nombre cae, sin desarrollar todavía. La frase central es la promesa estructural; las próximas secciones la desarman.

"Lo que falta no es otro wrapper. Es un protocolo común. Si tanto los hosts como los proveedores de capacidades acuerdan hablar el mismo formato, entonces vos escribís el server una vez y funciona en todos los hosts que hablen el protocolo. Ese protocolo existe, se llama Model Context Protocol — MCP — y lo propuso Anthropic en 2024. Pero acá viene lo importante: no es un producto de Anthropic. Es un estándar abierto que adoptaron Cursor, Codex CLI, OpenCode, y otros. Por eso lo vamos a estudiar — porque lo que aprendan acá viaja con ustedes a cualquier runtime que se sumen a usar."
