Este patrón ya pasó antes.

Dos precedentes históricos del mismo movimiento.

1991

HTTP

HyperText Transfer Protocol

browsers × servers

Antes de HTTP, cada browser hablaba con cada server por su cuenta, coordinando formatos a mano. Con un protocolo común, cualquier browser habla con cualquier server, sin acuerdo previo entre autores.

2016

LSP

Language Server Protocol

IDEs × lenguajes

Antes de LSP, cada IDE implementaba autocompletado para cada lenguaje por separado. Con un protocolo común, cada lenguaje publica un server y cualquier IDE lo consume.

MCP es el mismo movimiento, para agentes × capacidades. No inventa nada — aplica una idea conocida a un dominio nuevo.

Dos reveals — primero LSP, después la línea de cierre con MCP.

Dos precedentes históricos del mismo patrón, revelados de a uno. Ubican a MCP en una tradición — no es invento de Anthropic, es aplicar a agentes una idea que ya resolvió problemas análogos.

"Este movimiento que acabamos de ver — la matriz que se colapsa por un protocolo común — no es nuevo. Ya pasó dos veces en la historia reciente del software, y vale la pena ubicarlo donde lo vieron antes. Primero, HTTP. Año 91. HyperText Transfer Protocol. Antes de HTTP cada browser hablaba con cada servidor por su cuenta — coordinaban formatos, encodings, mecanismos. Después de HTTP, cualquier browser habla con cualquier server. Internet se vuelve posible. Esa es la propiedad del protocolo común: descomprime una matriz de coordinación humana en infraestructura compartida."

"Segundo, LSP — Language Server Protocol. 2016, Microsoft. Resolvió exactamente el mismo problema en el mundo de los IDEs. Antes, cada IDE — VS Code, Vim, Emacs, Sublime — implementaba autocompletado y go-to-definition para cada lenguaje — Python, Go, Rust, TypeScript — a mano. N por M. Insostenible. Después de LSP, cada lenguaje publica un language server, cada IDE consume cualquier server. N más M. Y eso es lo que hace que hoy cualquier IDE moderno tenga autocompletado decente en cualquier lenguaje, sin que el equipo del IDE escriba código específico para cada uno."

"MCP es el mismo movimiento, aplicado a agentes y capacidades. No inventa nada conceptualmente. Aplica una idea conocida — protocolo común — a un dominio donde el problema apareció hace poco."

Dos capas.

MCP se divide en data layer (qué se intercambia) y transport layer (por dónde).

capa interna

Data layer

Define qué se intercambia: discovery (server/discover), primitives, notifications. Wire format: JSON-RPC 2.0.

capa externa

Transport layer

Define por dónde viajan esos mensajes: canal físico y autenticación.

El mismo set de mensajes funciona idéntico sobre cualquier transport. No tenés que aprender JSON-RPC para usar MCP — sólo saber que está abajo.

Separación canónica data layer vs transport layer. La razón pedagógica importante: el mensaje es el mismo independiente del canal. Eso es lo que hace que el protocolo viaje entre transports.

"MCP se divide internamente en dos capas, y vale separarlas mentalmente. La data layer es la capa interna: define qué se intercambia entre cliente y server — el discovery inicial con server/discover, las primitives que vamos a ver en el próximo bloque, las notificaciones. Wire format JSON-RPC 2.0, formato viejo y aburrido, no hay nada que aprender ahí. La transport layer es la capa externa: define por dónde viajan esos mensajes, qué canal físico se usa y cómo se autentican. La propiedad clave es que el mismo set de mensajes JSON-RPC funciona idéntico sobre cualquier transport — eso es lo que le da la portabilidad al protocolo. No aprenden JSON-RPC para usar MCP, alcanza con saber que abajo hay un formato estándar."

Streamable HTTP transport

El server corre remoto y el host se conecta por red. HTTP POST + Server-Sent Events opcionales, sin sesión de protocolo. Auth por bearer token, API key o header propio — OAuth recomendado.

Regla simple: disco/red local → Stdio. Servicio compartido o de terceros → Streamable HTTP.

Los dos transports definidos por la spec. Lo importante es la regla de cuándo usar cada uno. La mayoría de los servers populares hoy son stdio.

"Los dos transports que la spec define. Stdio: el server corre como proceso local en la misma máquina que el host, es el modo en que el server vive con vos. Los mensajes viajan por stdin y stdout, cero overhead de red. La mayoría de los servers populares hoy son stdio: filesystem, git. Tu máquina los corre y listo. Streamable HTTP: el server corre remoto y el host se conecta por red. HTTP POST para mensajes cliente a server, con Server-Sent Events opcionales para streaming, y sin sesión de protocolo — cada request es independiente. La autenticación es bearer tokens, API keys o headers propios, con OAuth recomendado. Sirve cuando el server vive en un servicio compartido, como una instancia de Postgres centralizado, o cuando lo hostea un tercero, como GitHub. La regla simple es la del caption: disco o red local, stdio; servicio compartido o de terceros, Streamable HTTP."

Síntesis: el por qué pedagógico de las tres primitives. La diferencia de iniciativa determina permisos y UI. Esa es la razón estructural por la que MCP las separa.

"La síntesis. Por qué tres primitives distintas y no una sola con flags. La razón es que cada una tiene un dueño distinto de la iniciativa, y esa diferencia se propaga al resto del diseño. Los tools los decide el modelo, y eso implica un modelo de permisos de acción con confirmación. Los resources los decide la aplicación, eso implica permisos de lectura, transparentes, sin pedir nada. Los prompts los decide el usuario, eso implica invocación explícita, slash commands. Iniciativa distinta lleva a permisos distintos lleva a interfaz distinta: mezclar las tres en una sola primitive haría imposible un modelo de permisos coherente, porque el host no sabría cuándo pedir confirmación, cuándo cargar transparente, cuándo esperar al usuario. Por eso la spec separa."

"Primero, barra btw, de 'by the way'. Le hacés una pregunta al pasar y la respuesta no entra al historial ni te infla el contexto — aparece y se va. Ideal para chequear un detalle sin ensuciar la sesión en la que estás laburando. En Codex es barra side, o también barra btw. OpenCode no tiene nada parecido todavía."

"Segundo, barra rc, que es alias de barra remote-control. Deja la sesión disponible para controlarla desde claude.ai. Arrancás algo en la terminal de la oficina y lo seguís desde el celular. En Codex el equivalente es seguir desde la app de escritorio de ChatGPT, con barra app. En OpenCode no es exactamente lo mismo: vos levantás el servidor con opencode serve o opencode web, y te conectás con attach — la sesión la servís vos, no un tercero."

"Tercero, retomar sesiones. claude menos c retoma la última sesión de ese directorio, directo. claude menos r abre un picker para que elijas cuál. Es la forma de no perder el contexto de un día para el otro. En Codex es codex resume guión guión last, o codex resume para el picker. En OpenCode, opencode menos c o barra sessions."

"Y cuarto, para mí el más subestimado: barra rewind, o apretar Escape dos veces. Vuelve atrás no solo la conversación sino también el código, a un checkpoint anterior. Cuando una serie de cambios se fue al descenso, en vez de pelearte con git, hacés rewind. En Codex, Escape dos veces edita el mensaje anterior y bifurca la conversación, pero no toca los archivos. En OpenCode, barra undo sí revierte archivos además del mensaje, usando snapshots de git, y barra redo los vuelve a poner."
