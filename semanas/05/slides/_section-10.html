test-driven-development

Rojo, verde, refactor — en ese orden, sin excepciones.

Opener de §10. Cuarta skill del happy-path; pieza s10 iluminada en el roadmap.

"Cuarta skill: test-driven-development. Es la disciplina que opera dentro de cada tarea del plan. Mientras subagent-driven se ocupa de quién ejecuta qué, TDD dice cómo se ejecuta cada implementación: el test va primero, siempre."

El ciclo

1RED ✗ test fails

Escribís un test que describe lo que querés que haga el código. Lo corrés. Lo ves fallar.

→
2GREEN ✓ test passes

Escribís el mínimo código necesario para que el test pase. Nada de extras.

→
3REFACTOR ✓ aún pasa

Con el test en verde, limpiás el código sin romper nada. Después, arrancás otra vuelta con el próximo test.

Una vuelta por cada test. Código sin test previo se borra y se reescribe siguiendo el ciclo.

El ciclo canónico de TDD, con los colores tradicionales. La regla de hierro al final es el delta vs. el TDD "casero": código de prod sin test previo no se "guarda como referencia" — se borra.

"El ciclo tiene tres estaciones. RED: escribís un test que describe lo que querés que haga el código, lo corrés, lo ves fallar. GREEN: escribís el mínimo código necesario para que ese test pase. REFACTOR: con el test en verde, limpiás el código sin romper nada. Y vuelta a empezar con el próximo test."

"La regla de hierro: cualquier código de producción escrito antes de su test se borra y se reescribe siguiendo el ciclo. No se 'adapta', no se 'guarda como referencia' — se borra. Es disciplina, no perfeccionismo."

Cuándo se activa y por qué importa

Cuándo se activa

Por default — sí

Durante la implementación de cualquier feature, bugfix o cambio de comportamiento, antes de escribir código de producción. En los dos modos de ejecución.

Excepciones — con confirmación

Prototipos descartables, archivos de configuración, y código autogenerado por herramientas (ej. el openapi.yaml que produce FastAPI). Tienen que confirmarse explícitamente; no es el camino default.

Por qué importa

Sin TDD, el agente escribe código que parece correcto y después arma tests que pasan al primer intento. Esos tests escritos después del código validan lo que el código hace — no lo que vos querías que hiciera.

Y verde es toda la suite del proyecto, no solo tu archivo de test. Cada falla se reporta por nombre, aunque no la hayas causado vos.

Dos reveals — cuándo + por qué.

Cuándo se activa la skill y por qué la disciplina vale.

"Cuándo se activa: durante la implementación de cualquier feature, bugfix o cambio de comportamiento — antes de escribir código de producción. Si la tarea es agregar un endpoint, la skill arranca con un test del endpoint. Si la tarea es arreglar un bug, arranca con un test que reproduce el bug y falla por la razón correcta. Vale igual si el plan lo ejecuta un subagent por tarea o la misma sesión en modo Native: en Native, TDD es el único control por tarea que queda hasta la review final."

"Las únicas excepciones, que requieren confirmación explícita, son: prototipos descartables, archivos de configuración, y código autogenerado por herramientas — por ejemplo el openapi.yaml que produce FastAPI cuando le pedís el esquema. Esas tres no van por default por TDD; tienen que pedirse a propósito."

"Por qué importa: sin TDD, el agente escribe código que parece correcto y después arma tests que pasan al primer intento. Esos tests escritos después del código validan lo que el código hace, no lo que vos querías que hiciera — y por lo tanto pierden su valor como red de seguridad. Vos nunca los viste atrapar un bug. Y una regla que se agregó hace poco: verde quiere decir toda la suite del proyecto, no solo el archivo de test de la tarea. En pruebas, cuando la tarea nombraba un solo archivo, el agente corría solo ese en once de doce casos, y un test roto al lado pasaba desapercibido. Ahora corre el comando de tests del proyecto y reporta cada falla por nombre, incluso las que no causó."

El rastro de TDD, tarea por tarea

Task 1 tests del API existente: fijan lo que ya funciona → ✓ 11 passed
Task 2 ✗ ModuleNotFoundError: backend.auth → ✓ 31 passed
Task 3 ✗ 2 failed (falta el link de cerrar sesión) → ✓ 33 passed
fix ✗ 2 failed (falta la página /logged-out) → ✓ 34 passed

Al cerrar: 34 passed, 0 warnings — la suite entera, no el archivo de la última tarea.

Caso real: el rastro de TDD en la sesión del login con Auth0, sacado de los reportes de cada implementer.

"Acá está el rastro real de TDD en la sesión del login. La primera tarea es especial: escribe tests para el API tal como está, antes de tocar nada, así que esos 11 pasan desde el principio — su trabajo es fijar lo que ya funciona para que el login no lo rompa sin que nadie se entere. Desde ahí, cada tarea arrancó en rojo. La dos: el test del login falló porque el módulo de auth ni existía — ModuleNotFoundError. Después, 31 en verde. La tres: dos tests fallaron porque la página no tenía el link de cerrar sesión; después, 33. Y el arreglo final, igual: dos rojos, después 34."

"Y fíjense en el cierre: 34 passed y cero warnings, corriendo la suite entera del proyecto. El agente no se conformó con que pasaran los tests de la última tarea. Ese es el rastro auditable que deja TDD."
