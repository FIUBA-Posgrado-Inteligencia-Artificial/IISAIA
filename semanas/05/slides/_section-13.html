finishing-a-development-branch

Cuando todo está verificado, te muestra el menú y ejecuta tu elección.

Opener de §13. Séptima y última skill del happy-path; pieza s13 iluminada en el roadmap.

"Séptima y última skill del happy-path: finishing-a-development-branch. Cuando todas las tareas del plan están implementadas y verificadas, esta skill estructura las opciones de cierre y limpia el workspace según la que elijas. No decide por vos — te muestra el menú que corresponde al contexto y ejecuta la opción elegida con su cleanup correspondiente."

Tres opciones, sin estado intermedio

1Merge a main local

Checkout main, merge, corre los tests sobre el resultado, borra la branch local.

Trabajo local que no necesita revisión.

2Push + abrir PRdefault en GitHub Flow

Push de la branch y PR con la herramienta de tu forge. La branch queda viva para iterar feedback.

Para cualquier cambio que amerita revisión humana — casi siempre.

3Dejarla como está

Sin merge, sin push. La branch queda local con sus commits; la retomás con el plan.

Todavía no querés integrarla.

—Descartar: fuera del menú

Solo si lo pedís con esas palabras, y confirmás tipeando discard.

La skill nunca lo ofrece por su cuenta.

La regla central: no quedarse en estado intermedio. Una de las tres, no «después decido».

Las tres opciones que presenta la skill, en el orden en que aparecen en el menú. Desde la versión 6.2, descartar ya no está en el menú.

"La skill te muestra tres opciones, en este orden. La uno es merge a main local: checkout main, merge, corre los tests sobre el resultado mergeado y borra la branch. Es para trabajo que no necesita revisión humana. La dos es push y PR — el default en GitHub Flow y la más frecuente. Hace push de la branch y abre el PR con la herramienta de tu forge, sea GitHub u otra. La branch queda viva para iterar el feedback. La tres es dejarla como está: sin merge, sin push, la retomás después con el plan. Y fíjense en la cuarta caja, apagada. Versiones anteriores ofrecían 'descartar' al lado de 'merge', como una opción más. Se sacó: ofrecer borrar trabajo terminado y con tests en verde era una invitación al accidente. Ahora descartar solo pasa si vos lo pedís explícitamente, y tenés que tipear la palabra discard para confirmar. La regla central sigue: no quedarse en estado intermedio. Una de las tres, no 'después decido'. Branches dormidas son ruido en el repo y confusión para quien venga después, incluido vos mismo dentro de dos semanas."

Cuándo se activa y por qué importa

Cuándo se activa

Al final del plan

Después de que verification-before-completion pasó y el trabajo está listo para integrarse.

Si los tests fallan

El menú aparece recién con la suite en verde. Si algo falla, la skill frena y te muestra qué falló.

Por qué importa

Sin esta skill el flujo termina en «ya está, mergeá si querés». Esa decisión sin marco produce dos resultados malos típicos: se mergea a main algo que merecía revisión, o la branch queda viva indefinidamente y se convierte en deuda silenciosa.

La skill también ordena el cleanup: mergear primero, después verificar tests sobre el resultado, después remover worktree, y recién al final borrar la branch local. Saltearse ese orden produce errores feos.

Dos reveals — cuándo + por qué.

Cuándo se invoca + qué resultados malos evita.

"Cuándo se activa: al final del plan, después de que verification-before-completion pasó y el trabajo está listo para integrarse. Y un detalle: lo primero que hace es correr la suite entera. Si algo falla, no te muestra el menú: frena y te dice qué falló. Si te tenés que ir con el trabajo a medias, la branch simplemente queda como está y la retomás con el plan."

"Por qué importa: sin esta skill el flujo termina en 'ya está, mergeá si querés', y el humano queda decidiendo a ojo qué hacer con una branch que recién parió. Esa decisión sin marco produce dos resultados malos típicos. O se mergea a main algo que merecía revisión, o la branch queda viva indefinidamente y se convierte en deuda silenciosa que después nadie se anima a borrar porque no se acuerda qué tenía."

"La skill también ordena el cleanup: mergear primero, verificar tests sobre el resultado mergeado, después remover el worktree si aplica, y recién al final borrar la branch local. Saltearse ese orden produce errores feos — git branch -d falla si el worktree todavía referencia la branch, y git worktree remove falla en silencio si lo corrés desde adentro del worktree que estás intentando borrar."
