Cuatro comandos cubren el ciclo de vida

/plugin install <plugin>@<marketplace>

Descarga el plugin y registra sus skills, agents y commands. El @<marketplace> desambigua cuando tenés varios registrados.

/plugin update <plugin>

Actualiza a la última versión disponible según el campo version del manifest. Si el manifest no lo declara, cada commit es release nuevo.

/plugin uninstall <plugin>

Desinstala. Por default borra el directorio de datos persistente; pasale --keep-data si vas a reinstalar enseguida.

/plugin list

Lista lo instalado, con versión, marketplace de origen, y si está habilitado o no.

Los 4 comandos del ciclo de vida. Sintaxis exacta + frase corta de qué hace.

"Cuatro comandos cubren todo el ciclo de vida del plugin instalado."

"Install: descarga y registra. La sintaxis es slash plugin install, el nombre del plugin, arroba, el marketplace. Por ejemplo, install formatter at my-marketplace. El arroba marketplace desambigua de qué registro lo están sacando, importante cuando tienen varios registrados."

"Update: actualiza a la última versión disponible según el campo version del manifest que vimos en §2. Si el autor omitió version, Claude Code trata cada commit como release nuevo."

"Uninstall: desinstala. Por default también borra el directorio de datos persistente. Si querés conservarlo — por ejemplo porque vas a reinstalar una versión nueva en seguida — agregás --keep-data."

"List: muestra lo que tenés instalado, con versión, marketplace de origen, y si está habilitado o no. Es el comando que van a usar primero para verificar instalaciones."

Si usan Codex: /plugins abre el catálogo adentro de la sesión; desde la terminal, codex plugin add <plugin>@<marketplace>, codex plugin remove y codex plugin list. En OpenCode el ciclo es editar la lista "plugin" de opencode.json (o opencode plugin <paquete>).

El problema que ataca

Sin metodología

Le pedís algo → el agente arranca a tipear código → el desfasaje entre tu intención y su interpretación aparece tarde, con 20 mensajes y archivos commiteados.

Con metodología

Entendé qué construís → escribí el spec → planificá → ejecutá → verificá → mergeá.

Detectar el desfasaje en palabras es barato. En código ya escrito es caro.

Diagnóstico del problema. Comparación sin/con. El cierre martilla el costo del desfasaje tardío.

Cuatro principios, declarados en el README

Test-Driven Development

Tests primero, siempre. Un test escrito después del código valida lo que el código hace, no lo que vos querías que hiciera.

Sistemático antes que improvisado

Un proceso definido por encima de improvisar. Si no hay un proceso, lo estás inventando cada vez.

Complexity reduction

Simplicidad como objetivo primario. El código más simple que cumple es el correcto.

Evidence over claims

Verificar antes de declarar éxito. «Los tests pasan» sin el output al lado es una afirmación, no un hecho.

Tres conceptos, mínimo viable

1commit

Una foto del repo en un momento. Guarda QUÉ cambió (el diff), QUIÉN lo hizo, CUÁNDO, y POR QUÉ (mensaje del commit).

git add <archivos> git commit -m "tipo: descripción corta"

Regla práctica: commits chicos y frecuentes. Si no se describe en una sola oración corta, probablemente sean dos.

2branch

Una línea paralela de commits. main es la principal. Una branch propia (feature/<descripcion>) no contamina main mientras experimentás.

git checkout -b feature/<descripcion>

Mientras la branch está abierta podés romper, deshacer, reintentar — nadie más se entera.

3pull request

La propuesta de mergear tu branch a main. Tiene título, descripción, y queda visible para el equipo.

No es un comando local — se abre desde la UI de GitHub después del git push.

Hasta que no se mergea, la branch existe pero main no tiene esos cambios.

"Tres conceptos mínimos. El primero: commit. Una foto del repo en un momento — guarda qué cambió, quién, cuándo, y por qué. "Segundo: branch. Una línea paralela de commits. Main es la línea principal del proyecto. subagent-driven-development

Opener de §9. Tercera skill del happy-path; pieza s9 iluminada en el roadmap.

"Tercera skill: subagent-driven-development. Acá entramos al corazón del autonomous coding. La idea es ejecutar el plan despachando un subagent fresco por cada tarea, con un review automático entre tarea y tarea, y uno más sobre toda la rama al final. Vamos a ver por qué eso cambia todo."

Diagrama central de §9. El coordinador delega tarea por tarea a subagents efímeros con contexto aislado y elige el modelo de cada uno. Los números son los reales del log del login con Auth0.

"La estructura del flujo es así. Hay un coordinador — el agente principal — que mantiene la visión global: plan, spec, estado del repo. Y para cada tarea del plan, el coordinador despacha un subagent fresco. Fresco quiere decir literal: contexto limpio, sin la conversación del coordinador, sin decisiones tácitas de tareas anteriores. El subagent recibe su tarea, implementa, testea, commitea y devuelve un resumen. Miren el modelo de cada uno. Y la review final de toda la rama, a opus, el más capaz. Eso lo decide el coordinador tarea por tarea: si no nombrara el modelo, todo heredaría el de la sesión, que es el más caro. Por eso escala, y por eso el contexto del coordinador no se llena — lo vemos al final de la sección."

Cuándo se activa y por qué importa

Dos modos de ejecutar el plan

subagent-driven

Un subagent fresco y un reviewer por tarea, más una review final de toda la rama. El más completo; el más caro.

Native (executing-plans)

La misma sesión implementa todas las tareas, sin pausas, y hay una sola review al final. Más barato; sin review independiente hasta el final.

Por qué importa

Cada subagent arranca limpio, así no acumula context rot ni decisiones tácitas que se le filtraron en la Task 1 y le ensucian la Task 4.

El coordinador es el único que mantiene la visión global. El subagent no improvisa: lee plan y spec como contratos cerrados.

Dos reveals — los dos modos + por qué.

Los dos modos que ofrece el final de writing-plans, y la razón por la que el reset de contexto importa.

"Cuándo se activa: con un plan aprobado en disco, cuando elegís este modo al final de writing-plans. Son dos opciones. Subagent-driven: por cada tarea, un subagent fresco que implementa y un reviewer que la revisa antes de pasar a la siguiente; al final, una review de toda la rama. La alternativa se llama Native, y es la skill executing-plans: la misma sesión implementa todas las tareas de corrido, sin pararse a preguntarte, y hay una sola review al final con el modelo más capaz. Native es más barato y más rápido; lo que resigna es la mirada fresca en cada tarea. Con tres tareas que dependen una de la otra, Native alcanza. Con un plan largo, subagent-driven."

"Por qué importa el modo subagent: cada subagent arranca limpio, así no acumula context rot ni decisiones tácitas que se le filtraron en la Task 1 y le ensucian la Task 4. Cómo se opera y qué evitar

Dos cosas importantes

Decide, no te para

Ante una ambigüedad del plan, el coordinador decide, lo registra y sigue. Al final te muestra sus decisiones (rulings). Solo frena ante algo destructivo o irreversible.

Re-dispatch con feedback

Si el review encuentra issues, el fix vuelve al mismo implementer y un re-review mira solo esos hallazgos. Si no converge, sube de modelo.

Tres anti-patrones a evitar

Reusar el subagent «Que el mismo agente haga también la próxima tarea.»
Saltearse el review «Marcala como hecha y seguí a la próxima.»
Interrumpir mid-tarea Cualquier mensaje al coordinador mientras un subagent está corriendo.

Dos reveals — operativa + anti-patrones.

Detalles operativos del flujo + los tres anti-patrones que rompen la disciplina.

"Vamos a ver dos partes: cómo se opera el flujo mientras corre, y tres anti-patrones que lo rompen."

"Dos cosas importantes de la operativa. La primera: el coordinador no te para por cada duda. Si el plan tiene una ambigüedad o un conflicto, decide, anota qué decidió, por qué y cuánto cuesta si se equivocó, y sigue. Al final te muestra la lista de esas decisiones — la skill las llama rulings — para que las revises. Solo frena y te pregunta ante algo destructivo, irreversible, sensible de seguridad, o que sale de tu máquina, como un push. La segunda: si el review encuentra issues, el fix vuelve al mismo implementer, que ya tiene el contexto de la tarea, y un re-review mira solo esos hallazgos, no todo de nuevo. Si después de tres rondas no converge, cambia a un modelo más capaz; a la quinta, corta."

"Y tres anti-patrones. El primero: reusar el subagent — pasarle la tarea dos al mismo agente que hizo la uno. Arranca con su contexto cargado: el diff que generó, las decisiones que tomó, los errores que vio, y todo eso contamina la tarea siguiente. Cada tarea arranca fresca o no arranca. El segundo: saltearse el review. La consecuencia se siente dos tareas después, cuando estás debugueando algo que el reviewer habría atrapado en veinte segundos, y el costo de revertir crece porque hay tareas apoyadas sobre el error. El tercero: intervenir demasiado pronto. Si mientras una tarea corre le mandás un mensaje al coordinador para 'ayudar', rompés el loop. Para eso están los rulings al final."

Rojo, verde, refactor — en ese orden, sin excepciones.

Opener de §10. Cuarta skill del happy-path; pieza s10 iluminada en el roadmap.

"Cuarta skill: test-driven-development. Es la disciplina que opera dentro de cada tarea del plan. Mientras subagent-driven se ocupa de quién ejecuta qué, TDD dice cómo se ejecuta cada implementación: el test va primero, siempre."

El ciclo

1RED ✗ test fails

Escribís un test que describe lo que querés que haga el código. Lo corrés. Lo ves fallar.

→
2GREEN ✓ test passes

Escribís el mínimo código necesario para que el test pase. Nada de extras.

→
3REFACTOR ✓ aún pasa

Con el test en verde, limpiás el código sin romper nada. Después, arrancás otra vuelta con el próximo test.

Una vuelta por cada test. Código sin test previo se borra y se reescribe siguiendo el ciclo.

El ciclo canónico de TDD, con los colores tradicionales. La regla de hierro al final es el delta vs. el TDD "casero": código de prod sin test previo no se "guarda como referencia" — se borra.

"El ciclo tiene tres estaciones. RED: escribís un test que describe lo que querés que haga el código, lo corrés, lo ves fallar. GREEN: escribís el mínimo código necesario para que ese test pase. REFACTOR: con el test en verde, limpiás el código sin romper nada. Y vuelta a empezar con el próximo test."

"La regla de hierro: cualquier código de producción escrito antes de su test se borra y se reescribe siguiendo el ciclo. No se 'adapta', no se 'guarda como referencia' — se borra. Es disciplina, no perfeccionismo."

Cuándo se activa y por qué importa

Cuándo se activa

Por default — sí

Durante la implementación de cualquier feature, bugfix o cambio de comportamiento, antes de escribir código de producción. En los dos modos de ejecución.

Excepciones — con confirmación

Prototipos descartables, archivos de configuración, y código autogenerado por herramientas (ej. el openapi.yaml que produce FastAPI). Tienen que confirmarse explícitamente; no es el camino default.

Por qué importa

Sin TDD, el agente escribe código que parece correcto y después arma tests que pasan al primer intento. Esos tests escritos después del código validan lo que el código hace — no lo que vos querías que hiciera.

Y verde es toda la suite del proyecto, no solo tu archivo de test. Cada falla se reporta por nombre, aunque no la hayas causado vos.
